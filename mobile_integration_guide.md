# ZINGSA Collect: Mobile Integration Guide

This document outlines the end-to-end API integration flow for the mobile application (Flutter/Android/iOS) to communicate with the ZINGSA Collect backend. 

The backend runs on `http://172.30.5.24:8206` (or your production domain).

---

## 1. User Registration (Optional)
If a field officer does not have an account, they can register first. Note that an organization administrator must invite them to a project before they can download any forms.

**Request:** `POST /api/auth/users/`
```json
{
  "username": "field_officer_01",
  "email": "officer01@zingsa.test",
  "password": "StrongPassword123!",
  "first_name": "John",
  "last_name": "Doe"
}
```

**Response:**
```json
{
  "id": 2,
  "username": "field_officer_01",
  "email": "officer01@zingsa.test",
  "first_name": "John",
  "last_name": "Doe"
}
```

---

## 2. Authentication
The backend uses stateless JWT (JSON Web Tokens) for authentication.

### **POST `/api/auth/jwt/create/`**
Used to log the field officer into the system.
**Payload:**
```json
{
  "username": "zingsa_admin",
  "password": "SecureSeedPass2026!"
}
```
**Response (200 OK):**
```json
{
  "access": "eyJhbGciOi...",
  "refresh": "eyJhbGciOi...",
  "user": {
    "id": 1,
    "username": "zingsa_admin",
    "email": "admin@zingsa.test",
    "first_name": "",
    "last_name": ""
  }
}
```
> [!IMPORTANT]
> The mobile app must save the `access` token and attach it as a header `Authorization: Bearer <access_token>` to all subsequent requests.

---

## 2. Downloading Forms
Once authenticated, the mobile app needs to fetch the available forms so the officer can work offline.

### **GET `/api/forms/available/`**
Returns a list of all published forms that the field officer has permission to collect data for.
**Response (200 OK):**
```json
[
  {
    "id": "e4c1b9a2-...",
    "title": "Road Surface Quality Assessment",
    "status": "published",
    "current_version": {
      "id": "v123-uuid",
      "version_number": 1,
      "schema": {
        "title": "Road Surface Quality Assessment",
        "geometryType": "line",
        "questions": [
           { "id": "road_segment_id", "type": "text", "label": "Segment ID" },
           { "id": "defect_photo", "type": "image", "label": "Defect Photo" }
        ]
      }
    }
  }
]
```
> [!TIP]
> The mobile app should parse the `current_version.schema.questions` array to dynamically render the UI for data collection.

---

## 3. Data Sync Phase 1: Uploading Media
Because media files (photos, audio, videos) are large, they must be uploaded **before** the JSON data is synced to prevent timeouts.

### **POST `/api/media/upload/`**
Uploads a single media file.
**Headers:**
- `Content-Type: multipart/form-data`
- `Authorization: Bearer <token>`

**Payload:** 
- Form-data key `file` containing the binary file.

**Response (201 Created):**
```json
{
    "id": "b78d91c2...",
    "url": "http://172.30.5.24:8206/media/uploads/2026/05/pothole1.jpg",
    "original_name": "pothole1.jpg",
    "file_type": "image/jpeg",
    "file_size": 2048576,
    "created_at": "2026-05-27T10:00:00Z"
}
```
The mobile app must extract the `url` and store it locally against the specific record being synced.

---

## 4. Data Sync Phase 2: Bulk Submission Sync
After all media files are uploaded and their URLs injected into the answers payload, the app syncs the lightweight JSON data in bulk.

### **POST `/api/sync/submissions/bulk/`**
Syncs multiple records in a single atomic transaction.
**Payload:**
```json
{
  "device_id": "samsung-tablet-001",
  "submissions": [
    {
      "client_submission_id": "local-uuid-1",
      "form_version_id": "v123-uuid",
      "answers": {
        "road_segment_id": "SEG-001",
        "defect_photo": "http://172.30.5.24:8206/media/uploads/2026/05/pothole1.jpg"
      }
    },
    {
      "client_submission_id": "local-uuid-2",
      "form_version_id": "v123-uuid",
      "answers": {
        "road_segment_id": "SEG-002",
        "defect_photo": null
      }
    }
  ]
}
```

**Response (200 OK):**
```json
{
    "sync_log_id": "log-uuid-xyz",
    "total_received": 2,
    "total_success": 2,
    "total_failed": 0,
    "conflict_count": 0,
    "started_at": "2026-05-27T10:05:00Z",
    "finished_at": "2026-05-27T10:05:01Z",
    "submissions": [
        {
            "index": 0,
            "client_submission_id": "local-uuid-1",
            "status": "success",
            "submission_id": "backend-uuid-1"
        },
        {
            "index": 1,
            "client_submission_id": "local-uuid-2",
            "status": "success",
            "submission_id": "backend-uuid-2"
        }
    ]
}
```

> [!CAUTION]
> `client_submission_id` MUST be a unique ID generated by the mobile device. The backend uses this ID to prevent duplicate records if the network drops and the app retries the sync.
